HydrAI

GitHub Repository

HydrAI is an end-to-end wearable IoT sensing system designed for continuous, non-invasive hydration tracking, completed for Artificial Intelligence of Things [AIoT] (EECS 4764) in Fall 2025.

Design Motivation & Brainstorm

With hydration being such an important part of our everyday health, simply drinking a set “recommended” amount everyday is not good enough to ensure sustained cognitive and physical wellness.

Because monitoring hydration is highly reactive (by the time you’re thirsty, dehydration already set in fully), having real-time accurate recommendations is key. While the most accurate methods may require invasive methods (finger-prick blood/urine samples), the market non-invasive monitors (electrolyte analysis of sweat) can range from ~$200-$400.

The goal of this project was to design a low-cost, passive, continuous pipeline that estimates hydration trends with the help of Deep Learning.

System Architecture

We hoped to couple an embedded mixed-signal acquisition node with an asynchronous containerized cloud backend to ingest continuous biometric telemetry, aggregate it with mobile health metrics, and classify hydration status.

Using this architecture we looked to develop a prototype where multi-modal biometric indicators (Galvanic Skin Response (GSR), surface skin temperature, and heart rate) could be captured cleanly at the edge and streamed to a backend for feature extraction and classification.

Design Implementation

My Role & Focus: Backend Architecture, Cloud Deployment, and Data/ML Pipeline. (Collaborated with partners for analog sensor integration, breadboard layout, and data acquisition to train the hydration model).

HydrAI operates in a 4-stage pipeline: Data Collection, Edge Processing, Cloud Intelligence, and User Feedback. 

Hardware Sensing Node (Data Collection/Edge Processing)

The wearable device is built around an ESP32 microcontroller acting as the central hub. To ensure high-precision data acquisition, we utilized an ADS1115 Analog-to-Digital Converter to interface with analog biosensors. The sensor suite includes:

  • MAX3010: Captures photoplethysmography (PPG) data for Heart Rate variability.
  • GSR Sensor: Measures skin conductance (Galvanic Skin Response) to track sweat gland activity.
  • NTC Thermistor: Monitors real-time skin temperature.

Raw sensor data is transmitted via I2C/ADC to the ESP32, which forwards the payload via HTTP POST to a local edge gateway. A Python script (cloud_HRCalc.py) running on a gateway serves two roles:

  • [Preprocessing] Performs initial signal cleaning and raw value conversion.
  • [Forwarding] Forwards sensor data to the cloud backend container (POST / sensor_data) and manages the “Heartbeat” of the system by triggering the HTTP GET /recommendation on a set timer.
Cloud Backend & Deployment (Cloud Intelligence/User Feedback)

While the hardware sensing node captures continuous physical signals, the core of this project centers on the cloud backend and data fusion pipeline.

Rather than relying on raw biometric readings alone, the backend is designed as a multi-modal hub that fuses streaming telemetry, historical health context, real-time environmental APIs, and generative AI to deliver personalized, actionable hydration recommendations.

The core logic resides in a Dockerized FastAPI container hosted on Google Cloud Run. As demonstrated in the Cloud Script output, the local gateway aggregates real-time sensor readings from the ESP32 and transmits them to the cloud backend via the @sensor endpoint, while simultaneously triggering the decision engine through the @recommendation route.

The Google Cloud logs confirm the ingestion of this physiological data alongside asynchronous context updates from external Apple Health sources:

  • @/sensor: Ingests data from the hardware and processes the data to get a compatible format for the model
  • @/apple-health: Integrates external health context (Step Count, Active Energy) via the HealthKit Auto Export API. This data originates from an automation sync JSON in the Auto Export App linked to the users Apple Health Data
  • @/recommendation: The decision engine. It aggregates historical sensor trends, environmental context, and physical activity

This aggregated sensor data is fed into the Deep Learning Hydration Model to predict the user’s hydration state. The prediction, combined with weather and activity data, is sent to an LLM (via Poe API) to generate a natural language, actionable hydration tip.

The recommendation is delivered to the user’s smartphone via ntfy.sh (Pub/Sub notification service). This closes the data flow loop, providing the user with more contextual advice rather than generic “Drink Water!” reminders. This real-time processing highlights the system’s context-awareness when comparing the advice for people with no active data (0 steps/active calories) versus a more active user, ensuring recommendations are tailored to the user’s immediate physical exertion levels.

Design Process

When designing the backend architecture, I structured my approach from the outside in:

  1. Mapped the entire data flow by anticipating the exact inputs coming from edge sensors and the expected outputs required for the user interface. Defining this upfront made it easier to architect the processing layers in between!
  2. Developed Internal Components
    • Route Architecture: Designed the FastAPI endpoints (routes.py) around the anticipated data I/O.
    • Data Storage: Implemented an SQLite database to manage rolling time-series windows, allowing algorithms to compute based on most recent averages
    • Model Deployment: To eliminate added latency, I chose to package the trained hydration model directly in the backend memory
    • Background Tasks: Weather API queries and LLM prompt generation were isolated as asynchronous background services to prevent blocking the ingestion pipeline.
  3. Final Integration
    1. Collaborated on cloud_HRCalc.py as an edge bridge to solve Wi-Fi instability on the ESP32. The board now streams raw readings over a laptop hotspot, forwarding clean data to the cloud without dropping packets on the school’s network.
    2. Once the physical hardware and ML models were finalized, integrating the live data streams was straightforward, requiring only minor internal adjustments.

LESSON LEARNED: While working in parallel with the other parts of this project (ML Model, HW Sensor Data), writing dummy input scripts was a great way to test the type of data my routing could handle. Because my entire system could run standalone before the other components were finished, adapting to the final hardware and model was practically seamless.

Deep Learning Hydration Model

A deep learning architecture to estimates hydration levels from wearable sensor data.

Architecture: Sensor data is segmented into short time windows and processed by a pre-trained NormWear encoder, which converts raw biosignals into compact signal embeddings. A lightweight two-layer neural network classifier maps these embeddings to hydration states: hydrated, mildly dehydrated, or dehydrated.

Training & Optimization: The model is trained using labeled sensor windows and transfer learning to achieve high performance with limited data. Target hydration label classes were benchmarked against urine color charts during data collection runs. Parameters such as window size, learning rate, and classifier depth were tuned to balance classification accuracy and real-time efficiency.

Integration: The model is serialized and embedded directly into the backend container, allowing for low-latency inference on every API request without external dependencies.

TECHNICAL COMPONENTS (REFERENCE)

Hardware Layer

MCU: ESP32 Microcontroller (Wi-Fi enabled).

ADC: ADS1115 (16-bit precision for analog sensors).

Sensors:

  • MAX3010 (PPG/Heart Rate)
  • NTC Thermistor (Skin Temp)
  • GSR Module (Skin Conductance)

Software & Cloud

Backend: FastAPI (Python) for high-performance REST endpoints.

Containerization: Docker & Google Cloud Run for serverless deployment.

Database: SQLite/SQLAlchemy for sensor logging.

Notifications: ntfy.sh (Pub/Sub service).

AI & Data

ML Framework: PyTorch (Custom TFC-based Hydration Model).

LLM Engine: Poe API (Context-aware natural language generation).

External APIs:

  • OpenWeatherMap (Real-time weather).
  • Apple HealthKit (Activity metrics).

Further Exploration Areas

More Prototyping -> Transition from breadboard prototyping to a unified, custom PCB with compact sensors and an wrist enclosure for functional daily wear.

Manual User Inputs -> Introduce quick user inputs for water intake to track actual consumption against real-time monitoring.

Expand Model Capacity -> Add environmental context (heat index, humidity) and historical exertion (steps, active burn) into the core ML feature vector rather than aggregating them downstream at the prompt layer.
